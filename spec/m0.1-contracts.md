# M0.1 composition contracts

Frozen before implementation on 2026-10-11. The normative RFC sections 11.2 and 12.2 extend the accepted M0.0 kernel. The mechanism need is an external restricted client that selects one of two providers, optionally imports another service, and delegates named-resource authority through another native plugin.

## Import declarations

`#[import]` retains its M0.0 descriptor bytes and required semantics. `#[import(optional = "true")]` and `#[import(implementation = "plugin.id")]` lower to the fixed `phenix.import.v1` kind, with the same owner, Require role, contribution identity, provenance and operation. Its two added fields are `optional: Bool` and `implementation: Null | String`. This is a fixed import policy vocabulary, not extensible contribution kinds. The original `phenix.operation.v1` shape remains exact and rejects these added fields. Exact implementation names a plugin ID; it cannot be substituted. Duplicate operation imports reject even when policy differs.

Optional imports may remain unbound even when candidates exist. Calling an unbound declared optional import returns MissingBinding before any provider effect. Explicitly selected optional imports undergo the same schema and authority checks as required imports. No import selects a candidate implicitly.

## Deployment and resolution

`phenix.composition.v1` adds a public control-plane document with `artifacts`, `entry`, `bindings`, `grants`, `excluded`, `substitutions`, `authority`, and `resource`. Bindings contain `caller`, `interface`, `operation`, `provider`; grants contain `caller`, `interface`, `operation`, `resources`. `authority` contains sorted operation identities and named resources. `resource` is null or the named resource of the root invocation. Unknown fields reject.

The M0.0 deployment remains a frozen public profile. Both profiles normalize into the same resolver, immutable per-caller binding map, dispatcher and effect boundary. M0.0 global selections expand to the declared callers during that preparation. There is no adapter to the previous Phenix architecture.

All artifacts verify offline before loading. Exclusions remove plugin IDs before required dependency validation. Explicit substitutions map a selected provider ID to a replacement; duplicate, chained, cyclic or missing substitution targets reject. Substitutions never add artifacts or restore excluded providers. Exact requirements compare the effective provider with the declared ID and reject a different implementation.

All remaining artifacts are the explicitly installed composition. Every required import must have one compatible per-caller selection. Two clients can select different implementations of the same operation. Missing selection gives MissingBinding, or AmbiguousBinding when more than one compatible candidate exists. Required selected-import cycles reject with a deterministic plugin path before loading. Optional selected edges do not impose startup dependency order; invocation cycles still reject. Artifact, binding, grant and policy enumeration order must not change bindings or failures. All unordered inputs normalize before semantic traversal.

## Scoped host protocol

ABI 1.0 pointer layouts and ordinary operation invocations remain unchanged. Two versioned host-control selectors use the existing authenticated synchronous host callback:

- `phenix.host.scoped.v1` carries a canonical map with exactly `operation: String`, `request: Bytes`, `resource: Null | String`, and `authority: { operations: List<String>, resources: List<String> }`.
- `phenix.host.resource.v1` takes Null and returns Null or the current named resource String.

The public SDK offers typed `Host::invoke_scoped<O>` and `Host::resource`. These control messages carry restriction requests and resource identities, never host scope tokens or capability handles. Provider operations still enter the one dispatcher with their ordinary typed request. Context lookup authenticates scope/thread and exposes only the current resource identity; it neither resolves providers nor grants authority.

## Authority

`Authority` is a finite set of operation identities and named resource identities. Empty resources permit unscoped operations only. A named-resource operation requires the selected resource in the effective resource set. No wildcard exists. The root receives the trusted deployment ceiling. A nested call intersects its inherited authority, optional explicit restriction, authenticated caller grant, provider declaration ceiling and every active ancestor ceiling. Per-operation caller resource grants intersect inherited resources before provider entry. A request for broader authority cannot expand the inherited set.

A scoped call pins its named resource for its descendants. A child may narrow resources but may not switch from that pinned resource to another. An unscoped child inherits the parent's resource. Only a root or a parent without a pinned resource can choose a named resource within its effective set. Providers read the admitted resource through Host::resource; Core never interprets domain request fields.

## Acceptance

Nix must build all external fixtures through the SDK-only source distribution. Tests must prove distinct clients bind different providers, optional absence and explicit presence, exact implementation mismatch, substitutions and exclusions without fallback, deterministic required-cycle rejection, typed scope forwarding, narrowing through a relay, sibling-resource denial and unchanged protected counters. Constructor witnesses must remain absent for rejected preparation. Existing M0.0 gates remain required. A passing build alone does not accept this milestone.
