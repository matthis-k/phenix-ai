# M0.3 selectable generations

This addendum freezes RFC section 18 before generation lifecycle implementation. `tests/generation-identity-v1.json` and `tests/generation-identity.py` fix the encoding and hash vectors independently of the kernel. M0.2 admission, dispatch, scopes, tickets and physical leases remain the execution mechanism.

## Identity

The identity is lowercase SHA-256 of `b"phenix.generation.v1\0"` followed by the canonical Phenix Value encoding of a map with these exact keys. Every integer is U64. Lists and maps use the existing bounded wire profile.

| Key | Value |
| --- | --- |
| `artifacts` | Plugin-ID-sorted rows of `[plugin_id, artifact_sha256, descriptor_sha256, target, abi_major, abi_minor, features, execution]` |
| `authority` | The existing Authority map, with sorted operation and resource sets |
| `bindings` | Rows `[caller, operation_key, provider]`, sorted by caller then operation |
| `entry` | `[interface, operation, provider]` |
| `environment` | A validated, caller-attested identifier for the relevant environment configuration |
| `grants` | Rows `[caller, operation_key, sorted_resource_list]`, sorted by caller then operation |
| `resource` | Null or the selected resource identifier |

The resolved selected state is authoritative. Artifact paths, discovery order, rejected artifacts, original substitutions, constructor state and secrets do not enter the tuple. Environment identity describes configuration; it does not grant plugin authority or read ambient secret values. A caller must use a different identity when relevant environment configuration changes. Package digests bind the exact final executable bytes and generated descriptor bytes. Equality does not establish authenticity.

## Lifecycle and ownership

The trusted `Generations` owner installs a `Prepared` candidate. Installation validates identity and records offline inspection without loading code. Preparation remains `Prepared::prepare` or `prepare_composition`. `trial` loads through `Prepared::load`; a failed load records its failure and leaves the current default unchanged. There is no automatic promotion.

`promote` selects a loaded or explicitly activated candidate for new default roots. It may activate a prepared candidate with the same failure-atomic load operation. Assignment of the default happens only after activation succeeds. Selecting a prior eligible resident identity performs rollback. Promotion never mutates an existing generation or its policy.

`admit_default_root`, `admit_root_on` and scoped admission call the existing Kernel admission methods. A root owns a strong reference to its exact Kernel generation and uses the existing Root implementation. Each generation retains the serial M0 profile; roots on distinct generations can coexist. The owner does not add an executor, dispatch algorithm, host scope registry or authority store.

`retire` rejects the current default. It reports active admission and pending physical-lease blockers for a resident generation. Once all roots and work are quiet, it uses the existing ordered shutdown and releases the resident. Candidate retirement never starts code. Failed shutdown completes cleanup and reports the original failure. Dropping the generation owner leaves live root references intact. Dropping the final reference still obeys M0.2's rule to retain images if noncooperative work survives.

Inspection includes default identity, candidate/resident/failed states, canonical selected data, existing root/call/pending summaries and retirement blockers. It exposes neither scope handles nor wake permits. An environment identity is public configuration metadata.

## Required proof

Independent SDK-only `example-revision-a` and `example-revision-b` packages export the same contract and plugin ID with different executable bytes and responses. Their descriptors must be identical. Tests keep an A root pinned across B trial and promotion, call A again, admit a new B root, roll back to A and reject retirement while an A root or abandoned pending child remains live. Tests cover failed candidate startup, invalid policy, stale callback rejection, physical resource release, identity permutations and changes to every tuple component. The existing checks must continue to pass.

The kernel needs generation ownership because plugins cannot atomically select admission defaults or own and retire the executable images that implement their own host callbacks.
